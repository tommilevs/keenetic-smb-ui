## Зачем

Штатный SMB-сервер Keenetic занимает `192.168.1.1:445`. Он не умеет раздавать
агрегированное хранилище, не переносится на другой IP и не экспортирует диски
Proxmox. Этот проект добавляет **второй, независимый SMB-сервер**, который живёт
рядом со штатным:

```
штатный NDMS SMB   192.168.1.1:445   (не трогаем)
keenetic-smb-ui    10.30.0.2:445   (это приложение, Samba 4.24 из Entware)
```

Оба работают одновременно. Приложение держит свой `smbd`, свой `smb.conf`, свои
pid/state/private каталоги — SMB роутера продолжает работать как раньше.

## Возможности

- **Свой экземпляр Samba** под управлением приложения: отдельные конфиг, pid,
  state и passdb — ничего не конфликтует с NDMS.
- **Отдельный IP и интерфейс**: SMB слушает любой адрес на любом бридже
  (пример: `10.30.0.2` на `br0`), алиас `/32` приложение вешает само. Адрес и
  интерфейс меняются в настройках «SMB-сервер».
- **Агрегированная шара**: любое число внешних SMB-шар (диски Proxmox) и
  локальные USB-диски роутера собираются в одно дерево `\\IP\all`.
- **Переключатели по каждому диску**: добавление, правка, вкл/выкл и флаг
  «только чтение» прямо в веб-панели.
- **Пользователи роутера**: импорт из NDMS (`ndmc -c "show user"`) — у каждого
  свой пароль и флаг «только чтение».
- **Веб-панель** (русский интерфейс, тёмная тема): обзор, настройки SMB, диски,
  пользователи, живая статистика с графиками, лог Samba, обновления.
- **Статистика**: load average, память, трафик, SMB-сессии, занятость дисков и
  история для графиков — всё из `/proc` и `smbstatus`.
- **Автообновление**: панель проверяет GitHub Releases, скачивает нужный `.ipk`,
  ставит его через `opkg` и перезапускает службу.
- **Один статический бинарник**, без cgo и без зависимостей, кроме Samba и libc.

## Архитектура

```
              ┌──────────────────────── роутер (Entware) ─────────────────────────┐
              │                                                                    │
10.30.0.2 │  keenetic-smb-ui (Go, статический)                                 │
     :445     │    ├── smbd ────────────────► /opt/var/keenetic-smb-ui/share       │
 ─────────────┼──► │                                                               │
              │    ├── монтирования: //10.20.0.11/hddshare24tb-a (cifs, 2.1)  │
              │    │                //10.20.0.12/hdd24tb-b     (ro)          │
              │    │                //10.20.0.13/hddshare5tb-c (rw)          │
              │    │                                                               │
     :8099    │    └── веб-панель (встроенные ассеты, cookie-авторизация, JSON API) │
 ◄────────────┼──                                                                   │
              │                                                                    │
192.168.1.1   │  штатный NDMS SMB (445) — не трогаем                               │
              └────────────────────────────────────────────────────────────────────┘
```

Дополнительные модули ядра не нужны: приложение по требованию загружает штатный
`cifs.ko` и монтирует через SMB 2.1 — самый новый диалект, который поддерживает
ядро 4.9-ndm.

## Установка

```sh
opkg update
opkg install samba4-server samba4-client

# busybox wget на Keenetic без TLS — используем curl
curl -fsSL -O https://github.com/tommilevs/keenetic-smb-ui/releases/latest/download/keenetic-smb-ui_1.1.0_aarch64-3.10.ipk
opkg install ./keenetic-smb-ui_1.1.0_aarch64-3.10.ipk

/opt/etc/init.d/S99keenetic-smb-ui status
```

  >> /opt/etc/opkg.conf

## Веб-панель

Открой `http://<ip-роутера>:8099`, логин `admin`, пароль `lip368lip`
(меняется в «Настройках»). Все файлы интерфейса встроены в бинарник — ни CDN, ни
доступа в интернет не требуется.

| Раздел | Что делает |
|---|---|
| **Обзор** | состояние сервера, путь шары, сессии, трафик, графики нагрузки и трафика, занятость дисков |
| **SMB-сервер** | IP, бридж, рабочая группа, имя сервера, имя/путь шары, порты, протоколы, гость, только чтение, `force user`, доп. строки `smb.conf`, старт/стоп/рестарт, просмотр конфига |
| **Общие диски** | CRUD внешних шар, вкл/выкл, флаг «только чтение», живой статус монтирования |
| **Пользователи** | SMB-аккаунты, пароль и «только чтение», импорт из NDMS одной кнопкой |
| **Доступ к папкам** | матрица прав в стиле Keenetic: шары-папки, чтение/запись/запрет на пользователя, наследование |
| **Статистика** | uptime, load, память, сеть, SMB-сессии, график истории |
| **Логи** | хвост управляемого `samba.log` |
| **Настройки** | логин/пароль панели, адрес прослушивания, режим «только чтение», интервал статистики, обновления |

## Агрегированные диски

Любая SMB-шара, доступная с роутера, монтируется в экспортируемое дерево:

| Поле | Пример |
|---|---|
| имя | `hddshare24tb-a` |
| хост | `10.20.0.11` |
| шара | `hddshare24tb-a` |
| подкаталог (необязательно) | `proxmox` |
| логин / пароль | `admin` / `****` |
| только чтение | выкл / вкл |

Монтирование появляется как `\\<smb-ip>\all\hddshare24tb-a`. Локальные диски
роутера из `/tmp/mnt/*` подставляются автоматически как `local-<uuid>`.

`подкаталог` монтирует только папку внутри шары — та же идея, что поле
**«Подкаталог»** в Proxmox для SMB/CIFS-хранилищ. Удобно, когда нужен, например,
только `proxmox` (образы VM, ISO, дампы) или только `storage/llama/models`, а не
весь диск целиком.

**Чужие шары — по умолчанию «только чтение».** На хостах Proxmox часто нет прав
записи для обычного Samba-пользователя; помеченные строки монтируются `ro`, чтобы
клиент получал предсказуемый отказ вместо «сломанной» записи.

Внешняя шара должна уметь SMB2.1 или ниже (это предел ядерного CIFS-клиента
Keenetic), а учётные данные — быть реальными SMB-аккаунтами на той стороне.

### Как подключены диски нескольких хостов Proxmox (пример)

Именно под такую схему делался проект: три диска с трёх разных машин Proxmox.
Адреса ниже — заглушки, подставь свои:

| Роль | Хост | Шара | Аккаунт | Режим |
|---|---|---|---|---|
| 24 ТБ HDD на хосте A | `10.20.0.11` | `hddshare24tb-a` | `svc-smb` | только чтение |
| 24 ТБ USB-диск на хосте B | `10.20.0.12` | `hdd24tb-b` | `svc-smb` | только чтение |
| 5 ТБ HDD на хосте C | `10.20.0.13` | `hddshare5tb-c` | `svc-smb` | чтение и запись |

Что получается на роутере (`10.30.0.2` — отдельный адрес SMB этого приложения):

```
\\10.30.0.2\all
├── hddshare24tb-a   → //10.20.0.11/hddshare24tb-a
├── hdd24tb-b        → //10.20.0.12/hdd24tb-b
├── hddshare5tb-c    → //10.20.0.13/hddshare5tb-c
└── local-<uuid>     → USB-диски роутера
```

Пошаговая инструкция, готовый фрагмент `smb.conf` для стороны Proxmox, опции
монтирования и таблица диагностики:
**[docs/proxmox-disks.ru.md](docs/proxmox-disks.ru.md)**

## Права на папки

Раздел **Доступ к папкам** сделан диалогом «Файлы и папки» один-в-один с
веб-конфигуратором Keenetic (NDMS 5.x, тёмная тема): заголовок, тулбар 40×40,
шапка таблицы `#2F3745`, строки 55 px, активная строка `#2E3D57`.

- Слева дерево настоящих папок шары: раскрытие по уровням, иконки, размеры.
  Размеры локальных дисков считаются рекурсивно; для сетевых CIFS-дисков
  показывается `—`, чтобы рекурсивный обход 24 ТБ не нагружал Proxmox.
- Справа панель «Права доступа к выбранной папке»: для каждого пользователя
  NDMS выбор из трёх уровней — **Чтение и запись**, **Только чтение**,
  **Доступ запрещен**. Правило действует на вложенные папки, пока в них нет
  своего правила (наследование как в Keenetic).
- «Создать папку» создаёт каталог в выбранной папке, «Обновить» перечитывает
  дерево, «Сохранить» применяет права и перезапускает Samba.

Кроме флага у аккаунта, в панели есть матрица прав в стиле Keenetic (**Доступ к
папкам**): каждая папка внутри агрегированного дерева публикуется отдельной
SMB-шарой со своим списком пользователей.

- Уровни доступа на пользователя: **запрещён**, **чтение**, **чтение и запись**.
- Правило действует и на вложенные папки, пока в них нет своего правила.
- Два пользователя на одной папке: `admin` — чтение и запись, `vms` — чтение:
  `admin` может копировать файлы, `vms` только смотрит. Проверено на живом Samba.
- Общая шара `all` получает `read only = yes` + `write list` из прав корня:
  пользователи без права записи видят дерево, но не могут в него писать.
  Остальные подключаются напрямую к своей папке
  (`\\<smb-ip>\disk-c`, `\\<smb-ip>\snippets`, …).
- Ограничения делает сам Samba: в сгенерированных секциях стоит `read only = yes`
  и явный `write list`, поэтому не нужны ни POSIX ACL, ни xattr на смонтированных
  CIFS-дисках.

Шары папок выглядят в `smb.conf` как обычные секции и видны в списке шар:

```ini
[disk-c]
   path = /opt/var/keenetic-smb-ui/share/proxmox-100-5tb
   read only = yes
   valid users = admin vms
   write list = admin
   force user = root
```

## Пользователи

Два способа завести SMB-аккаунты:

1. **Вручную** — логин, пароль, «только чтение», вкл.
2. **Импорт из роутера** — читает `ndmc -c "show user"`, поэтому аккаунты,
   заведённые в веб-интерфейсе Keenetic, появляются одной кнопкой. Пользователи
   NDMS уже есть в `/etc/passwd` — именно это нужно бэкенду `tdbsam`.

Пароли записываются через `smbpasswd`, хранилище паролей роутера не трогается.

## Обновления

Панель обращается напрямую к GitHub Releases API:

- **Проверка** сравнивает текущую версию с последним тегом и выбирает ассет под
  архитектуру устройства (`opkg status keenetic-smb-ui`, затем `uname -m`).
- **Установка** скачивает `.ipk` через `curl`, запускает
  `opkg install --force-reinstall` и перезапускает службу в фоне. Конфиг помечен
  как `conffile`, поэтому переживает обновление.

## Конфигурация

`/opt/etc/keenetic-smb-ui/config.json` (права `0600`), все поля редактируются в UI:

```jsonc
{
  "web": { "listen": "0.0.0.0:8099", "user": "admin", "password": "…", "readonly": false },
  "smb": {
    "enabled": true,
    "listen_ip": "10.30.0.2",
    "bind_device": "br0",
    "workgroup": "WORKGROUP",
    "server_string": "keenetic-smb-ui",
    "share_name": "all",
    "share_path": "/opt/var/keenetic-smb-ui/share",
    "share_readonly": false,
    "force_user": true,
    "ports": "445",
    "min_protocol": "SMB2",
    "max_protocol": "SMB3_11",
    "users": [ { "name": "admin", "password": "…", "readonly": false, "enabled": true } ],
    "guest_ok": false,
    "extra_options": []
  },
  "remotes": [
    { "id": "nas-a", "name": "hddshare24tb-a", "host": "10.20.0.11",
      "share": "hddshare24tb-a", "user": "admin", "password": "…",
      "enabled": true, "readonly": true }
  ],
  "stats": { "interval_sec": 5, "history_len": 120 }
}
```

`force_user: true` заставляет Samba работать внутри шары от root. Это нужно, потому
что агрегированное дерево смешивает root-овые CIFS-монтирования и диски роутера.

## Безопасность

- Панель: HTTP basic + `HttpOnly` cookie-сессия, опциональный режим «только
  чтение». Если панель торчит наружу — закрывай правилами самого роутера.
- SMB: сгенерированный `smb.conf` использует `map to guest = never`, явный
  `valid users` и выбранные тобой порты; шара экспортируется только на заданном IP.
- Секреты лежат только в `config.json` (права `0600`) на роутере.
- Приложение запускает `smbd` от root, потому что ему нужно читать и писать в
  агрегированные монтирования — считай панель административной поверхностью.
