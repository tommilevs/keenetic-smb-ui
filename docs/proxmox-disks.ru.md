# Подключение дисков Proxmox к общей шаре

Инструкция описывает ровно ту схему, под которую делался проект: несколько хостов
Proxmox раздают свои диски по SMB, роутер монтирует их и отдаёт одним общим деревом.
**Все адреса, имена шар и аккаунты ниже — примеры-заглушки**, подставь свои.

## Пример инвентаря

| Роль | Хост (пример) | Шара (пример) | Аккаунт | Режим |
|---|---|---|---|---|
| 24 ТБ HDD на хосте **A** | `10.20.0.11` | `hddshare24tb-a` | `svc-smb` | только чтение |
| 24 ТБ USB-диск на хосте **B** | `10.20.0.12` | `hdd24tb-b` | `svc-smb` | только чтение |
| 5 ТБ HDD на хосте **C** | `10.20.0.13` | `hddshare5tb-c` | `svc-smb` | чтение и запись |

Что получится на роутере (раздаёт `keenetic-smb-ui` на своём IP):

```
\\10.30.0.2\all
├── hddshare24tb-a     → //10.20.0.11/hddshare24tb-a
├── hdd24tb-b          → //10.20.0.12/hdd24tb-b
├── hddshare5tb-c      → //10.20.0.13/hddshare5tb-c
└── local-<uuid>       → локальные диски роутера из /tmp/mnt/*
```

`10.30.0.2` — отдельный адрес SMB этого приложения; штатный SMB роутера со своим
адресом не затрагивается.

## 1. Подготовить шару на каждом хосте Proxmox

На узле Proxmox шара описана в `/etc/samba/smb.conf`:

```ini
[hddshare24tb-a]
   path = /mnt/hddshare24tb-a
   browseable = yes
   guest ok = no
   read only = no
   valid users = svc-smb
   write list = svc-smb
   force user = root      # нужно, если каталог принадлежит root
```

Важные моменты:

- В `valid users` должен быть аккаунт, который использует роутер (`svc-smb`).
- Диски, смонтированные Proxmox, обычно принадлежат `root`, поэтому обычный
  Samba-пользователь писать в них не может. `force user = root` (и `write list`)
  решают это. Если не хочешь так делать — просто пометь диск как **RO** на роутере.
- После правки перезапусти Samba: `systemctl restart smbd`.
- Если аккаунта нет: `smbpasswd -a svc-smb`.

Быстрая проверка с любой Linux-машины со `smbclient`:

```sh
smbclient //10.20.0.11/hddshare24tb-a -U 'svc-smb%<пароль>' -m SMB3 -c 'ls'
```

## 2. Добавить диск в веб-панели

Открой панель, раздел **Общие диски → Добавить диск** и заполни строку:

| Поле | Пример | Смысл |
|---|---|---|
| имя | `hddshare24tb-a` | имя папки внутри `\\<smb-ip>\all` |
| хост | `10.20.0.11` | хост Proxmox с SMB |
| шара | `hddshare24tb-a` | имя SMB-шары (без косой черты) |
| логин | `svc-smb` | SMB-аккаунт на том хосте |
| пароль | `••••••` | его пароль |
| вкл | вкл | монтировать при применении |
| RO | вкл/выкл | монтировать только для чтения |

Повтори для каждого хоста, нажми **Сохранить список** и **Применить** (кнопка
справа сверху). Панель перегенерирует `smb.conf`, перемонтирует включённые диски и
перезапустит управляемый `smbd`; на дашборде видно статус каждого диска.

Строки с **RO** монтируются с опцией `ro`. Это правильный выбор, когда удалённая
сторона не даёт записи: клиент получит понятное «только чтение» вместо
`ACCESS_DENIED` посреди копирования.

## 3. Что приложение делает под капотом

Для каждого включённого диска выполняется примерно это:

```sh
insmod /lib/modules/$(uname -r)/cifs.ko      # однократно, если модуль не загружен
mount -t cifs //10.20.0.11/hddshare24tb-a /opt/var/keenetic-smb-ui/share/hddshare24tb-a \
  -o vers=2.1,username=svc-smb,password=…,uid=0,gid=0,file_mode=0775,dir_mode=0775, \
     iocharset=utf8,nounix,serverino,actimeo=10,nomapposix
```

Почему именно такие опции:

| Опция | Причина |
|---|---|
| `vers=2.1` | ядерный CIFS-клиент Keenetic (4.9-ndm) умеет только SMB 2.0/2.1, на 3.0+ получаем `EINVAL` |
| `uid=0,gid=0,file_mode/dir_mode` | дерево раздаётся от root, владельцы должны быть единообразны |
| `actimeo=10` | меньше ревалидаций, чем с `1`, и меньше сюрпризов с устаревшими dentry |
| `nounix,serverino` | Samba на Proxmox не согласует POSIX-расширения |
| `nomapposix` | не нужно преобразование имён SMB для обычных имён файлов |

Сама раздача использует `force user = root` в секции `[all]` — иначе Samba
работает от подключающегося пользователя и не может писать в root-овые монтирования.

## 4. Проверка

На роутере:

```sh
mount | grep cifs                       # по строке на смонтированный диск, с опциями
ls /opt/var/keenetic-smb-ui/share       # дерево агрегации
smbclient //<smb-ip>/all -U 'admin%<пароль>' -m SMB3 -c 'cd hddshare24tb-a; ls'
```

С компьютера: открыть `\\<smb-ip>\all` и проверить, что все подпапки открываются.
Диски в режиме RO должны давать понятную ошибку доступа при попытке что-то создать.

## 5. Если что-то не работает

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `tree connect failed: NT_STATUS_ACCESS_DENIED` при монтировании | неверный аккаунт или имя шары | проверить `valid users` и имя шары, тест через `smbclient` |
| `mount error: EINVAL` | неподдерживаемая опция или SMB 3.x | оставить `vers=2.1`, убрать NFS-опции вроде `retrans=` |
| `mount error(2): No such file or directory` | шару не видно под этим аккаунтом | проверить путь через `smbclient -L` |
| запись падает с `ACCESS_DENIED`, чтение работает | Samba на удалённой стороне работает не от root и не может писать в каталог | добавить `force user = root` на хосте Proxmox или пометить диск **RO** |
| монтирование есть, но папка пустая | смонтировалось до того, как шара стала доступна | нажать **Применить** ещё раз, посмотреть логи |
| `umount: target is busy` | Samba держит открытые файлы | остановить Samba в панели, применить, запустить снова |

Общее правило: один набор данных должен раздавать **один** SMB-сервер. Если
переэкспортировать шару, которую Proxmox уже отдаёт напрямую по SMB, получаются два
писателя на одни файлы и проблемы с кэшем.
